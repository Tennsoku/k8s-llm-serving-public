# M1 Review — Single-Node vLLM Baseline

<section id="m1-overview" class="review-fragment" data-analysis-status="final">
<h3>M1 总结</h3>
<p><strong>takeaway：</strong>M1完成单台DGX Spark上四种request-unique workload的canonical replay。Short-input至C16未观测到queue pressure；Long-input在C16已有pressure但仍有并发承载余量，long-long boundary sweep至C64仍未触及hard capacity boundary。三个runtime OVAT与0.5B/7B comparison只作PoC和reference。</p>
<h4>scope</h4><ul><li>覆盖M1.3 historical reference、四份M1.4 canonical analysis、三份M1.5 runtime OVAT、M1.5 long-long boundary analysis与M1.6 small/medium comparison。</li><li>M1.4使用request-unique cache identity。四种workload各重放3个预声明并发点+3次repetition，以repetition汇总取median。</li><li>该 milestone 结论限定于单节点/固定model+runtime/workload，不适用于双节点DGX或生产集群。精确指标与限制请参看各run analysis及summary。</li></ul>
<h4>claims</h4><ul><li><code>observed_fact</code> 四个M1.4 canonical workload均完成三个预声明并发点的三次replay；M1.5 boundary与M1.6 small/medium也完成各自声明的exploratory范围。</li><li><code>interpretation</code> Pressure行为取决于workload：short-input至C16未观测到waiting；long-input在C16已有pressure但仍有未量化的并发承载余量，long-long的C64仍只是highest tested。</li><li><code>interpretation</code> 三个runtime OVAT与0.5B/7B comparison只作 poc 和 reference。</li></ul>
<h4>limitations</h4><ul><li>Canonical analysis只覆盖各config声明的并发点，不是完整scaling curve；highest tested不是capacity boundary。</li><li>Long-long的realized output length随concurrency漂移，限制了跨点throughput/TPOT/E2E的结论。</li><li>三个runtime OVAT的repetition/sampler interval/case contract不完全匹配，只作descriptive comparison。</li><li>Boundary sweep每点只有一次repetition且存在输出形状漂移，不用于canonical tail-latency/stability/正式C_pressure；C64以上未测试。</li><li>M1.6两侧均为exploratory且每点一次repetition；tokenizer/runtime revision未捕获，也未执行质量评估，仅覆盖short-long C1/C8。</li></ul>
<h4>handoff</h4><ul><li><code>m2</code><ul><li>复用M1的request-level measurement与request-unique cache baseline，为prefix-cache、量化、投机解码和长上下文分别声明workload、实验axis与tested range；具体任务与exit criteria以Roadmap的M2为owner。</li><li>需要因果结论时匹配repetition、sampler interval、case contract与realized token shape；量化同时报告质量结果或compatibility boundary，投机解码报告acceptance rate与无收益/负收益场景。</li></ul></li><li><code>m3</code><ul><li>以M1.4单节点裸机canonical replay作为Kubernetes单副本开销对照，在匹配model、image、workload、cache identity与measurement context后报告不可匹配项。</li><li>复用M1 benchmark client验证probe、cold/warm model cache与Pod termination；在声明范围内报告success、failure与truncation，并在Pod环境重新测量operating references，不直接复用裸机阈值。</li></ul></li></ul>

<h3>Long-long bounded boundary</h3>
<p><strong>takeaway：</strong>在长输入/长输出的设计场景中，并发从 C16 提高到 C64 后 256 个请求仍全部成功，但 TTFT p95 从 1.56 秒飙升至 16.78 秒，峰值排队请求数从 13 增至 56，输出吞吐量相对只增加约 9%。这说明服务已经进入明显的 pressure 区。不过C64 只是本次测试的最高并发，不是容量上限，正式的 pressure boundary 仍需确认。</p>
<h4>operating_references</h4><ul><li><code>c1</code> · <code>not_applicable</code> · concurrency=<code>null</code> · 本次边界测试从 C16 开始，C1 基线仍以 long-long canonical analysis 为准。</li><li><code>c_eff</code> · <code>not_applicable</code> · concurrency=<code>null</code> · 本次测试主要目的在于观察高并发压力，不重新选择效率参考点。</li><li><code>c_pressure</code> · <code>unknown</code> · concurrency=<code>null</code> · C16–C64 已有直接的排队与延迟压力证据，但只有一次 repetition且实际输出长度发生漂移+没有失败请求且未到硬容量边界，仍有冗余空间。不申明压力点。</li><li><code>highest_tested</code> · <code>observed</code> · concurrency=<code>64</code> · C64 的全部请求成功，测试按预定并发范围正常结束。它是测试上限，容量上限未知。</li></ul>
<h4>claims</h4><ul><li><code>observed_fact</code> 4/4 个测试点数据完整且通过 raw validation；C16/C32/C48/C64 共 256 个请求全部成功，无 failure 或 timeout。run outcome 为 success，未发生 OOM 或 restart。</li><li><code>observed_fact</code> C16/C32/C48/C64 的 output TPS 为 920.25/899.50/916.43/1004.71，TTFT p95 为 1.56/4.73/9.88/16.78 秒，max waiting 为 13/27/43/56；实际 output/request 同时从 334.33 漂移到 451.17 tokens。</li><li><code>interpretation</code> 并发扩大 4 倍时，记录的输出吞吐量仅增加 9.18%，而 TTFT 与等待请求数持续上升，构成直接的排队压力证据；但单次 repetition 与输出长度漂移尚不足以确定可复现的压力点。</li><li><code>unknown</code> 在预声明的 C16–C64 范围内未观测到硬容量边界：C64 的全部请求仍然成功，run 以 sweep_completed 而非 stop condition 结束。该 Unknown 指 C64 以内。</li></ul>

<section id="m1-max-model-len" class="review-fragment" data-analysis-status="final">
<h3>max_model_len · 8192 → 16384</h3>
<p><strong>takeaway：</strong>在long-long shape的C8单点测试中，将max_model_len从 8192 提高到 16384 后，candidate完整成功，吞吐与延迟仍处于与baseline相近的范围。由于采样间隔、case contract和repetition数量略有区别，该结果只作为参考，不发布强因果结论。</p>

<section id="m1-small-medium" class="review-fragment" data-analysis-status="final">
<h3>Qwen2.5-0.5B → Qwen2.5-7B</h3>
<p><strong>takeaway：</strong>在同一节点，同一 short-long workload，相同 non-model runtime parameter 下，Qwen2.5-0.5B 和 Qwen2.5-7B 的 C1/C8 exploratory runs 均完成全部请求，且未观测到 waiting requests。7B BF16 路径由此验证到 C8，但其 output throughput 在两点均更低，TTFT/TPOT/E2E 均更高。该结果只作为这两个固定 model artifacts 的 sizing ref，不作为 canonical tail-latency/容量/模型质量排名。</p>
<h4>claims</h4><ul><li><code>observed_fact</code> 两侧 C1/C8 共 4 个 measured cases 均完整，256 requests 全部成功，无 failure/timeout；两个 run 均通过 raw validation。sweep状态返回success，shutdown lifecycle 也成功。</li><li><code>observed_fact</code> 两侧实际 token shape 一致；在 C1 和 C8，7B candidate 的 output throughput 均低于 0.5B baseline，TTFT/TPOT/E2E 均更高。两侧 max waiting 均为 0。</li><li><code>interpretation</code> 两侧均未观测到 waiting，因此没有直接证据把性能差异归于 queue pressure。model_identity 可以认为是单一逻辑 axis，不过不能单独归因于参数量，tokenizer/runtime revision 也可能影响性能。</li></ul>
<h4>limitations</h4><ul><li>两份 run 均为 exploratory，且每个 concurrency case 只有一次 repetition。不作为 canonical/tail-latency claim。</li><li>tokenizer/runtime revision 未捕获，本实验也没有评估输出质量，不能把性能差异简化为单变量的参数量的效应。</li><li>只覆盖 short-long workload 的 C1/C8。兼容性结论不解释为完整容量、scaling curve 或 small/medium model 排名。</li></ul>
